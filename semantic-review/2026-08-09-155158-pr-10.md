# 협업 커서 렌더링, viewer 자기 caret, 이탈 시 presence 회수

Tiptap `CollaborationCaret`을 배선해 원격 커서·선택 영역을 그리고, 실제 Chromium 2컨텍스트로 그 렌더링을 검증하는 테스트 계층(`test/browser/`)을 새로 만들었다. 그 검증이 잡아낸 결함 2건을 함께 고친다 — viewer가 자기 커서를 못 보는 문제는 쓰기 정책을 건드리지 않고 ProseMirror widget decoration으로 렌더링만 보충했고(`src/page/localCaret.ts`), 새로고침 시 상대 화면에 약 33초 남던 유령 커서는 `pagehide`에서 `awareness.setLocalState(null)`로 명시 회수한다. 인증 쪽은 presence 라벨의 출처가 되는 프로필을 토큰과 같은 메모리 세션에 묶고, 최신 인증 시도만 commit·rollback할 수 있게 소유권을 고정했다.

**Watch for**: `setLocalState(null)`은 되돌릴 수 없다 — y-protocols의 `setLocalStateField`·하트비트·y-websocket의 재접속 재발행이 **전부 `getLocalState() !== null` 가드 뒤에 있어서**, bfcache/freeze 복귀 후에는 presence가 영구히 발행되지 않는다(mechanism **confirmed**, 도달성 **likely**). 소켓이 이미 닫힌 상태의 회수는 큐잉 없이 버려지므로 회수는 보장이 아니라 최선노력인데, 3초 예산 테스트는 이것을 결정론처럼 고정한다(**confirmed**). 읽기 전용 범위 선택 불가를 고정한 `expect(...).toBe(false)`는 박스 중심(=텍스트 아래 빈 공간)을 클릭하므로 제약이 풀려도 계속 통과할 수 있다(**confirmed**). `/api/users/me`는 backend `main`에 없어서 이 PR이 먼저 배포되면 presence가 아니라 로그인 전체가 실패한다(**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

presence 회수는 "생성-소멸 짝짓기"의 절반만 닫혀 있다. `pagehide`에서 로컬 awareness를 null로 만드는 것은 정상 이탈에 대해 정확하지만, 그 null이 **재무장 불가 상태**라는 점이 코드 주석의 전제("bfcache 복귀 시 다시 발행된다")와 어긋난다. 복귀·재접속 경로에서 presence를 다시 세우는 지점이 필요하다.

회수의 전달 자체에도 보장이 없다. y-websocket은 소켓이 열려 있지 않으면 프레임을 버리고 재시도하지 않으며, 게이트웨이는 불투명 릴레이라 세션이 닫혀도 제거 프레임을 대신 만들지 못한다. 그래서 유령 제거는 떠나는 클라이언트의 협조에만 의존하고, 협조가 불가능한 경로(크래시·강제 종료·네트워크 단절·백오프 창)는 모두 33초 폴백으로 떨어진다. 이 실패를 구분하는 클라이언트 신호는 없다.

Phase 3에서 회수 프레임 자체는 불투명 awareness 프레임이므로 Redis fan-out을 그대로 탄다. 형태가 바뀌는 것은 **되살림 반경**과 **fail-open의 복구 논거**다 — join 재질의가 인스턴스 경계를 넘으면 유령을 쥔 peer 풀이 넓어지고, Redis 장애 중에는 "다음 커서 이동이 곧 복구"라는 §3.4 논거가 회수에는 성립하지 않는다(떠난 클라이언트에게 다음 이동이 없다).

widget decoration 선택은 문서 모델을 오염시키지 않는다. 위젯은 뷰 상태 전용이고 클립보드는 DOM이 아니라 문서 슬라이스에서 만들어지므로 복사·저장·수렴 경로에 새는 지점이 없다. 다만 관측된 라벨 텍스트 누출은 로컬 caret이 아니라 같은 PR의 원격 caret 렌더러에 남아 있고, 로컬 caret에 적용한 `aria-hidden` 한 줄이 그쪽에는 빠져 있다.

브라우저 계층은 이 PR의 가장 큰 자산이다 — 컨텍스트 분리로 BroadcastChannel 우회를 배제한 판단과 UI 단정에 게이트웨이 카운터를 붙인 판단은 둘 다 "보이니까 됐다"를 거부한다. 그 위에서 몇 개의 단정은 주장보다 약하다: 부재 단정에 대기가 없고, 카운터에 룸 라벨이 없어 델타가 이 룸에 귀속되지 않으며, 읽기 전용 제약을 고정한 단정은 양성 대조가 없다.

인증 세션의 소유권 고정은 stale 응답이 최신 세션을 덮는 경로를 정확히 닫았다. 남는 것은 결합 문제다 — presence 라벨용 프로필 조회를 인증 완성 조건으로 승격했고, 그 엔드포인트는 아직 backend `main`에 없다.

### `setLocalState(null)`은 재무장할 수 없다

`pagehide` 핸들러는 `provider.awareness.setLocalState(null)` 한 줄이다. 그 호출이 남기는 상태가 문제다 — `states`에서 자기 clientID가 삭제되고 `getLocalState()`가 영구히 `null`을 반환한다. 그리고 presence를 다시 발행할 수 있는 모든 경로가 그 null 뒤에 잠긴다:

```
y-protocols/awareness.js:141  setLocalStateField(field, v)
                                → const state = this.getLocalState()
                                → if (state !== null) { ... }        // null이면 no-op
y-protocols/awareness.js:53   하트비트 자가 갱신
                                → if (this.getLocalState() !== null && ...)
y-websocket/src/y-websocket.js:210  websocket.onopen 재발행
                                → if (provider.awareness.getLocalState() !== null) { send }
```

세 가드가 함께 닫히므로, `pagehide` 이후 페이지가 **살아 있는 채로 복귀하는** 경로에서는 다음이 모두 일어나지 않는다: 소켓 재연결 시 자기 상태 재발행, 15초 하트비트 갱신, 그리고 `CollaborationCaret`이 `setLocalStateField('user', ...)`로 이름을 다시 싣는 것(`extension-collaboration-caret/dist/index.js:83`), y-tiptap cursor plugin이 `setLocalStateField('cursor', ...)`로 커서를 싣는 것(`y-tiptap/dist/y-tiptap.js:2200`). 후자 둘은 플러그인 view가 재생성돼도 여전히 field setter라서 no-op이다. 회복 경로는 `Awareness` 인스턴스를 새로 만드는 것뿐이고, 그것은 effect 재실행(= 컴포넌트 리마운트) 또는 전체 리로드에서만 일어난다.

따라서 `Editor.tsx`의 주석 — "bfcache로 복귀하면 소켓이 이미 닫혀 재연결되고 그때 presence가 다시 발행되므로 회수해도 안전하다" — 는 성립하지 않는다. 재연결은 일어나지만 발행은 가드에 막힌다. 결과는 **나는 남을 보는데 남은 나를 못 보는** 상태이고, 이것은 이 PR이 고친 결함 ①(남들은 내 커서를 보는데 나만 못 본다)과 같은 종류의 비대칭이 방향만 뒤집힌 것이다. 심지어 더 조용하다 — 결함 ①은 본인이 즉시 알아차리지만, 이쪽은 본인 화면에 아무 변화가 없다.

`pagehide`를 고른 이유(`unload` 폐기·bfcache 진입 차단·모바일 미발화)는 정확하다. 다만 `pagehide`를 고르면 **복귀가 존재한다**는 것을 함께 받아들이게 되고, 그때 `pageshow`(또는 Page Lifecycle의 `resume`)에서 `setLocalState({ user: awarenessUser })`로 재무장하는 짝이 필요하다. `pagehide` 시 `event.persisted`로 분기해 bfcache 진입에서는 회수하지 않는 선택도 있지만, 그러면 복귀하지 않고 폐기되는 경우에 유령이 남는다 — 회수하고 재무장하는 쪽이 두 경우를 모두 덮는다.

도달성에 대한 한 가지 유보: Chromium이 WebSocket이 열린 페이지를 실제로 bfcache에 넣고 `pagehide`를 `persisted=true`로 발화하는지는 이 검토에서 실측하지 않았다. 확인 방법은 브라우저 계층에 `goto(other) → goBack()` 케이스를 넣고 상대 화면에서 라벨이 돌아오는지 보는 것이다. 모바일 백그라운드 전환(freeze)은 같은 이벤트를 쓰므로 같은 경로다.

### 소켓이 닫힌 뒤의 회수는 조용히 사라진다

회수 프레임은 awareness `update` 이벤트를 타고 `broadcastMessage`로 간다:

```
y-websocket/src/y-websocket.js:232
  const broadcastMessage = (provider, buf) => {
    const ws = provider.ws
    if (provider.wsconnected && ws && ws.readyState === ws.OPEN) { ws.send(buf) }
    if (provider.bcconnected) { bc.publish(...) }
  }
```

큐도 재시도도 없다. 소켓이 열려 있지 않으면 프레임은 그 자리에서 사라지고 호출자에게 아무것도 알려주지 않는다. 열려 있지 않은 시점은 드물지 않다 — 재접속 백오프 창(최대 2500ms), `messageReconnectTimeout` 무응답 감지로 닫힌 직후, 지하철·엘리베이터 같은 네트워크 단절, 모바일 라디오 절전. 이 경로에서는 회수 프레임이 나가지 않으므로 상대 화면에 33초 유령이 그대로 남는다. 그리고 이것이 앞 절과 겹치면 최악의 조합이 된다: 전달은 실패하고 로컬 상태만 영구 null이 된다.

정상 이탈에서도 전달은 최선노력이다. `ws.send()`는 프레임을 소켓 버퍼에 넣고 반환하며, 그 버퍼가 페이지 폐기 전에 플러시되는지는 스펙이 보장하지 않는다(측정된 2ms는 Chromium 로컬 환경의 결과다). `sendBeacon`이나 `fetch(keepalive)`에 있는 이탈 시 전송 보장이 WebSocket에는 없다.

구조적 대책이 서버에 없다는 것도 같은 그림의 일부다. 게이트웨이 `afterConnectionClosed`는 `rooms.leave`와 브리지 정리만 하고 awareness 제거 프레임을 합성하지 않는다 — 페이로드를 해석하지 않는다는 불변식(plan §1.2) 때문에 떠난 clientID를 알 수 없어서 **못 한다**. 즉 유령 제거는 설계상 떠나는 클라이언트의 협조에만 의존하고, 협조가 원리적으로 불가능한 경로(프로세스 크래시, 탭 강제 종료, OS kill)는 전부 33초 폴백이다. 그것 자체는 수용 가능한 선택이지만, 코드와 테스트는 회수를 보장처럼 다룬다 — 3초 예산이 그 표현이다. 예산을 짧게 잡아 폴백 경로를 강제하는 판단은 옳고, 그 예산이 **소켓이 열린 정상 reload** 하나만 덮는다는 사실이 어디에도 적혀 있지 않은 것이 문제다.

회수가 실패했는지 아는 방법도 없다. 클라이언트에 계측이 없고, 게이트웨이 카운터는 릴레이된 프레임만 세므로 "보내지 않은 프레임"은 어느 쪽에도 신호를 남기지 않는다. 이 배선이 조용히 죽는 회귀를 단위 테스트가 잡아주지만(좋은 판단이다), 런타임에 조용히 실패하는 경우는 잡히지 않는다.

### Phase 3에서 형태가 바뀌는 지점

회수 프레임 자체는 Phase 3를 잘 통과한다. 게이트웨이 관점에서 그것은 다른 awareness 프레임과 구분되지 않는 불투명 바이트이므로 `awareness:{docId}` fan-out을 그대로 타고 인스턴스 경계를 넘는다. 계획서 §3.1이 저장 키를 0개로 유지한 결정이 여기서 배당을 준다 — 반영할 서버 상태가 없으니 회수도 릴레이만으로 끝난다.

바뀌는 것은 되살림 반경이다. 저자가 실측한 부활의 정확한 메커니즘은 clientID 세대 차이다 — 새로고침한 클라이언트는 새 `Y.Doc`, 즉 **새 clientID**로 돌아오므로 자기 과거 clientID의 `meta.clock`을 모른다. 그 상태에서 join 재질의를 받은 peer가 아직 타임아웃하지 않은 유령을 포함한 전체 상태를 응답하면, `applyAwarenessUpdate`가 `clock > 0`으로 그것을 적용한다. (이미 타임아웃으로 지운 peer는 `meta.clock`이 남아 같은 clock의 재생을 거부한다 — 그래서 부활은 새로 들어온 세션에만 나타나고, 이것이 "새로고침한 본인만 자기 유령을 본다"를 설명한다.)

Phase 3 §3.2는 join 시 `awareness:query:{docId}`를 발행해 **모든 인스턴스**의 peer에게 재질의하고, 그 응답은 질의자만이 아니라 룸 전원에게 간다(§3.2가 N² 버스트로 이미 경고한 성질). 유령을 쥔 peer가 어느 인스턴스에 있어도 신규 세션에 도달하므로 부활 확률은 인스턴스 수만큼 올라간다. 회수가 성공하는 경로에서는 문제가 없고, 회수가 실패한 경로(위 절의 목록)에서 33초 창이 더 잘 뚫린다는 뜻이다.

fail-open과의 상호작용은 더 분명한 구멍이다. §3.4는 Redis 장애 시 "상태가 없으니 복구도 없다 — Redis가 돌아오면 다음 커서 이동이 곧 복구다"로 근거를 세운다. 그 논거는 **가산 상태에만** 성립한다. 회수는 떠난 클라이언트가 보내는 마지막 프레임이고 다음 이동이 없으므로, 장애 중 유실된 회수는 영구 유실이다. 크로스 인스턴스 peer는 33초 타임아웃으로만 정리된다. 즉 이 프론트엔드 수정의 보장 수준은 정확히 §3.4가 발동하는 순간 최선노력으로 내려간다. 수용 가능하지만(상한이 33초로 묶여 있다) 계획서에 예외로 적혀야 한다.

presence 소유권이 인스턴스 밖으로 나가는 시나리오는 더 크다. §3.1이 보류한 `presence:{docId}` Hash를 나중에 도입하면, 게이트웨이는 페이로드를 해석하지 않으므로 회수 프레임을 **릴레이는 하지만 Hash에는 반영하지 못한다.** 서버 상태에 유령이 영구 잔존하고, join 시 그것을 재생하면 클라이언트의 33초 타임아웃 청소도 무력화된다(재생마다 `lastUpdated`가 갱신되므로). 이 수정은 "어떤 서버 컴포넌트도 presence 상태를 갖지 않는다"는 불변식에 암묵적으로 의존한다. 그 의존을 `Editor.tsx` 주석에 한 줄 남기는 값이 크다 — Hash를 도입하는 사람이 프론트엔드 회수 경로를 함께 봐야 한다는 신호가 된다.

### widget decoration은 문서 모델에 닿지 않는다

`Decoration.widget`은 `props.decorations`에서만 생성되고 문서 노드를 만들지 않는다. Y.Doc에는 아무것도 들어가지 않으므로 저장·수렴 경로에 새는 지점이 없다. 복사도 안전하다 — ProseMirror 클립보드는 라이브 DOM이 아니라 `selection.content()` 슬라이스를 직렬화한다(`prosemirror-view/dist/index.js:3672` → `serializeForClipboard`). 위젯은 슬라이스에 없으므로 클립보드 텍스트·HTML 어디에도 나타나지 않는다. 로컬 caret은 텍스트 없는 빈 `<span>`이고 `aria-hidden="true"`가 붙어 있어 `textContent` 누출도 만들지 않는다. 하네스의 `documentText`가 `.local-caret`까지 제거하는 것은 방어적 여유이지 필요 조건은 아니다.

누출은 다른 쪽에 남아 있다. 같은 PR의 `renderRemoteCaret`(`Editor.tsx:33~45`)은 라벨에 `aria-hidden`을 붙이지 않는다. 하네스 주석이 기록한 실측 현상(`"three" + "Diag Viewer"`가 블록 `textContent`에 합쳐진다)은 테스트만의 문제가 아니라 접근성 트리와 브라우저 페이지 검색에 같은 형태로 나타난다 — 스크린리더는 peer가 커서를 옮길 때마다 그 이름을 문서 본문 중간에서 읽는다. CSS의 `user-select: none`은 네이티브 선택만 줄이고 접근성 트리에는 영향이 없다. 로컬 caret에 적용한 한 줄이 원격 caret에는 빠진 비대칭이다.

경계 정규화는 이 파일에서 잘 잡혀 있다. `safePresenceColor`가 고정 hex 형식만 통과시키고 `style.borderColor` 프로퍼티 대입을 쓰므로, 기본 구현의 `setAttribute('style', ...)`가 열어두는 CSS 선언 삽입 표면이 닫힌다(plan §1.5가 수용한 신원 위조 범위 안에서 할 수 있는 최선이다). `colorForUserId`가 clientID 대신 서버 UUID를 해시하므로 재접속·다중 탭에서 색이 흔들리지 않는다.

widget decoration에 안정 키를 준 판단은 `WidgetType.eq`의 참조 동일성 폴백을 정확히 짚었다. 키가 없으면 원격 타이핑이 만드는 매 트랜잭션마다 caret `<span>`이 재생성돼 깜빡임 애니메이션이 0프레임에서 다시 시작한다 — 증상이 "불규칙한 점멸"이라 원인을 애니메이션 CSS에서 찾게 되는 종류의 버그다.

### 테스트가 주장하는 것과 실제로 고정하는 것

읽기 전용 범위 선택 단정이 가장 약한 지점이다. `tryRangeSelect`는 `page.click('.editor .tiptap', { clickCount: 3 })`으로 요소 **박스 중심**을 클릭한다. `.editor .tiptap`은 `min-height: 240px`(`src/index.css:173~180`)이고 이 시나리오의 문서 내용은 1280px 폭에서 한 줄이므로, 중심 좌표는 텍스트가 없는 빈 공간이다. 그러면 `false`는 "읽기 전용에서는 범위 선택이 불가능하다"의 증거가 아니라 "빈 공간을 세 번 클릭했다"의 결과일 수 있다. 같은 파일의 케이스 3·4는 `box.y + 28`로 첫 줄을 정확히 찍는 기법을 이미 쓰고 있어서, 고치는 비용도 낮다.

그리고 이 단정에는 양성 대조가 없다. `selectParagraph`는 별개 함수이고 실패 시 예외를 던지므로, **같은 헬퍼가 editable 화면에서 `true`를 낸다**는 확인이 어디에도 없다. 대조가 없으면 "제약이 풀리면 이 테스트가 실패해서 알려준다"는 알람이 울리지 못할 수 있다 — 제스처가 텍스트에 닿지 않는 한 제약이 풀려도 계속 `false`다. 제약을 단정으로 고정한 판단 자체는 옳다(측정된 제약을 조용히 방치하지 않는다). 고정하려는 대상이 제3자 동작이므로, 그 단정이 실제로 그 동작만을 측정한다는 것을 대조로 보여야 값이 생긴다.

이어지는 `expect(await remoteSelectionCount(editorPage)).toBe(0)`은 대기 없는 부재 단정이다. 릴레이가 느리면 항상 통과하므로 "selection이 발행되지 않았다"와 "아직 도착하지 않았다"를 가르지 못한다. 같은 스위트가 존재 단정에는 `waitUntil`로 시간 근거를 붙이는데 부재 단정에는 아무것도 없다.

케이스 5의 주석은 `ws_write_dropped_total{reason=viewer}`를 근거로 들지만 테스트는 그 카운터를 읽지 않는다. 실제로 `editable: false`가 트랜잭션을 로컬에서 막으므로 프레임이 나가지도 않아 그 카운터는 0이다 — 주석이 설명하는 게이트웨이 드롭 경로는 이 케이스가 통과시키지 않는다. 그 불변식은 `test/e2e`의 Node 클라이언트가 덮으므로 커버리지 구멍은 아니고, 주석이 이 케이스의 범위를 넘어서 말하고 있다.

게이트웨이 카운터를 독립 증거로 붙인 판단은 이 하네스에서 가장 값진 부분이다 — UI만으로는 BroadcastChannel 우회와 서버 경로를 구분할 수 없다는 진단이 정확하고, `gatewayCounter`가 접두사 오합산과 `NaN` 전파를 막으려고 경계를 강제한 것도 부트스트랩 실패를 동작 실패로 오인하지 않게 한다. 다만 `SessionMetrics.awarenessRelayed`/`awarenessQuerySent`는 태그 없는 전역 카운터다(`SessionMetrics.java:71,83`). 델타는 "이 게이트웨이에서 awareness가 릴레이됐다"까지만 말하고 "이 룸의 이 presence가 릴레이됐다"를 말하지 못한다 — 이전 실행에서 살아남은 재접속 루프나 다른 탭이 같은 델타를 올린다. `> 0` 단정이라 방향성은 지키지만, 우회 경로를 배제하는 증거로서는 룸 라벨 없이는 약하다.

CI에 갇힌 불변식은 다음이다: 늦은 join의 3초 예산, 크로스 컨텍스트(= 게이트웨이 통과) 경로, 유령 회수의 실측, 원격 selection 렌더링, viewer 자기 caret이 **실제로 그려지는지**. 단위 테스트가 배선의 존재/부재를 잡도록 함께 둔 판단은 옳고 실제로 잘 좁혀져 있다 — `pagehide` 발화, 리스너 등록/해제의 핸들러 참조 동일성, `.local-caret`의 존재(viewer)·부재(editor). 남는 간극은 예산과 렌더 품질, 그리고 서버 경로다. `focusEditorSurface`가 합성 `FocusEvent`를 던지므로 `document.activeElement`는 바뀌지 않는다 — 플러그인 상태 기계는 검증되지만 실제 포커스가 caret을 만든다는 것은 브라우저 계층에만 있다(y-tiptap의 커서 발행은 `view.hasFocus()`를 보므로 이 둘은 다른 조건이다).

부수로, 하네스가 문서화한 BroadcastChannel 우회는 프로덕션에도 같은 형태로 존재한다. README가 권하는 "editor/viewer를 두 탭에 나눠 여는 데모"가 정확히 그 형태이므로, 그 데모에서는 게이트웨이 경로가 검증되지 않는다. 앱에 `disableBc: true`를 줄 것인지는 테스트가 아니라 제품 결정이니 어딘가에 판단으로 남기면 좋다.

### 인증 세션 소유권과 크로스 레포 결합

`beginAuthenticationAttempt`가 객체 identity로 소유권을 발급하고 `setToken`·`setAuthenticatedUser`·`clearToken`이 boolean/열거로 결과를 돌려주는 구조는, 지연된 응답이 최신 세션을 commit하거나 rollback하는 경로를 정확히 닫는다. `signUpAndSignIn`이 exported `signIn`을 다시 부르지 않고 같은 owner로 `completeSignIn`을 이어 가는 것도 세대 증가를 한 번으로 묶는 데 필요하다 — 주석이 "두 번째 clear가 false가 되어 실제 실패를 stale로 오인한다"까지 남긴 것이 이 코드를 나중에 만질 사람에게 실제로 유용하다. `LoginForm`의 `latestSubmit` ref와 두 겹인데, 각각 UI 상태와 세션 상태를 막으므로 중복이 아니다.

결합이 문제다. `completeSignIn`은 `/api/users/me` 실패를 `clearToken(owner)` + throw로 처리하므로 프로필 조회 실패는 로그인 실패다. 그 엔드포인트는 backend `main`에 없고 `feat/m3-phase2-current-user`(PR #35)에 있다 — 이 PR이 먼저 배포되면 presence 라벨이 아니라 **로그인 전체가 실패한다.** 머지 순서를 고정해야 한다.

설계 질문도 함께 남는다. presence 라벨용 프로필을 인증 완성 조건으로 승격하면 인증 가용성이 부가 엔드포인트에 묶인다. `presence.ts`에는 이미 `FALLBACK_PRESENCE_NAME`이 있어 degrade 경로가 존재하는데 쓰지 않았다. "토큰과 프로필이 모두 준비돼야 완전한 세션"이라는 불변식의 단순함과 가용성 결합 비용 중 어느 쪽을 택했는지는 근거를 남길 만하다 — fail-closed는 인가 판단에 맞는 기본값이지만 이 값은 인가에 쓰이지 않는다.
