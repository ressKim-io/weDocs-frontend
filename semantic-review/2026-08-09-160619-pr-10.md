# viewer 자기 caret 보충, 이탈 시 presence 회수, 2브라우저 presence 하네스

Playwright 실 Chromium **2컨텍스트**로 협업 presence를 관측하는 새 테스트 계층(`test/browser/`)을 만들고, 그 계층이 잡아낸 결함 2건을 고쳤다. viewer가 자기 커서를 못 보던 문제는 쓰기 정책(`editable: false`)을 건드리지 않고 ProseMirror widget decoration으로 렌더링만 보충했고(`src/page/localCaret.ts`), 새로고침 시 상대 화면에 ~33초 남던 유령 커서는 `pagehide`에서 `awareness.setLocalState(null)`로 명시 회수한다. 같은 컨텍스트 두 탭이 BroadcastChannel로 게이트웨이를 우회한다는 진단에서 컨텍스트 분리를 끌어내고, UI 단정에 게이트웨이 카운터를 병행한 판단은 둘 다 "보이니까 됐다"를 구조적으로 거부한다.

**Watch for**: `pagehide`는 **마지막 콜백이 아니다** — 모바일 백그라운드 discard·탭 강제 종료는 발화 없이 끝나고, Page Lifecycle이 보장하는 마지막 지점은 `visibilitychange:hidden`이다(**confirmed**). 회수가 성공한 뒤 로컬 상태가 영구 `null`이 되면 15초 자가 갱신도 함께 멈추는데, 그 하트비트가 **Phase 3 §3.4 fail-open의 복구 엔진**이고 룸에 혼자 남은 경우 30초 주기 재접속 flap까지 만든다(**confirmed / likely**). 코드와 계획서가 인용하는 "33초 폴백"은 **전역 상한이 아니다** — 유령을 쥔 peer가 join 재질의에 응답하면 새 세션에서 `lastUpdated`가 갱신돼 33초가 다시 시작되고, 이 사슬은 join이 이어지는 동안 계속된다(**confirmed**). 이 수정의 동기였던 **되살림 경로 자체는 어떤 테스트도 덮지 않는다** — 케이스 6은 새로고침 후 로그인 화면에서 멈추고 재접속하지 않는다(**confirmed**). 하네스는 dev 빌드(StrictMode 이중 마운트) 위에서 돌아 페이지 1개 열기가 WS 세션 2개를 만들므로, 카운터 델타를 "이 세션이 서버를 통과했다"의 증거로 쓰기 어렵다(**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

`pagehide` 회수는 정상 이탈에 대해 정확하지만 **보장이 아니라 최선노력**이고, 코드·테스트·계획서가 그것을 보장처럼 취급한다. 도달하지 못하는 경로는 세 종류다 — 이벤트가 아예 발화하지 않는 경로(모바일 discard·강제 종료·크래시), 발화했지만 소켓이 닫혀 프레임이 큐 없이 버려지는 경로(재접속 백오프·네트워크 단절), 그리고 발화·전송 모두 성공했지만 그 성공이 로컬 presence를 재무장 불가 상태로 남기는 경로(bfcache 복귀).

세 번째가 이번 패스의 핵심이다. 회수 이후 `getLocalState()`가 영구 `null`이 되면 y-protocols의 15초 자가 갱신이 함께 멈춘다. 그 하트비트는 keep-alive가 아니라 두 가지를 떠받치고 있다 — y-websocket의 `messageReconnectTimeout` 무응답 감지를 면하게 해주는 유일한 자체 트래픽이고, Phase 3 §3.4가 "Redis가 돌아오면 다음 커서 이동이 곧 복구다"의 근거로 명시한 복구 메커니즘이다. 회수가 그것을 끄면 룸에 혼자 남은 세션은 30초 주기로 스스로 연결을 끊고 재접속하며, Phase 3에서는 그 클라이언트가 fail-open 복구 대상에서 영구히 빠진다.

유령의 수명 상한도 코드 주석이 말하는 것과 다르다. `applyAwarenessUpdate`는 처음 보는 clientID를 적용할 때 `lastUpdated`를 **수신 시각**으로 새로 찍는다. 유령을 아직 타임아웃하지 않은 peer가 join 재질의에 자기가 아는 전체 상태로 응답하므로, 새로 들어온 세션은 이미 30초 늙은 유령을 **자기 기준 33초** 동안 새로 쥔다. join이 이어지는 동안 이 사슬은 끊기지 않는다. 즉 회수가 실패한 경로의 비용은 "최대 33초"가 아니라 "누군가 계속 들어오는 동안"이고, Phase 3 §3.2에서 재질의가 인스턴스 경계를 넘으면 사슬이 붙을 수 있는 peer 풀이 인스턴스 수만큼 넓어진다. 게이트웨이가 join 질의를 3명으로 제한한 것(`MAX_QUERIED_PEERS_ON_JOIN`)이 사슬을 좁히지만 끊지는 않는다.

Phase 3에서 이 수정이 주는 안전감은 조건부다. 회수 프레임 자체는 불투명 바이트라 `awareness:{docId}` fan-out을 그대로 타고 인스턴스 경계를 넘는다 — §3.1이 저장 키를 0개로 유지한 결정이 여기서 배당을 준다. 형태가 바뀌는 것은 실패 쪽이다: 되살림 반경이 넓어지고, fail-open의 복구 논거가 회수에는 성립하지 않으며(떠난 클라이언트에게 다음 이동이 없다), 나중에 `presence:{docId}` Hash를 도입하면 게이트웨이가 회수 프레임을 릴레이만 하고 서버 상태에는 반영하지 못한다. 이 수정은 "어떤 서버 컴포넌트도 presence 상태를 갖지 않는다"에 암묵적으로 의존한다.

widget decoration 선택은 문서 모델을 오염시키지 않는다 — 위젯은 뷰 상태 전용이고, `LocalCaret`이 활성인 화면은 정의상 범위 선택조차 불가능한 viewer 화면이라 복사 경로가 비어 있다. 관측된 라벨 텍스트 누출(`"three" + "Diag Viewer"`)은 같은 PR의 원격 caret 렌더러에 남아 있고, 로컬 caret에 적용한 `aria-hidden` 한 줄이 그쪽에는 빠져 있다. 하네스의 `documentText`가 데코레이션 클래스를 제거하고 텍스트를 읽는 방식은 그 누출을 구조적으로 가린다.

하네스가 CI에 갇혀 있다는 사실보다 **무엇이 갇혔는지**가 더 중요하다. 갇힌 것은 예산(늦은 join 1ms, 유령 회수 2ms), 게이트웨이 통과 경로, 렌더 품질이다. 그리고 갇히지도 않은 것이 둘 있다 — 이 수정의 동기였던 되살림 경로와 caret이 포커스를 잃으면 사라지는 경로는 어느 계층에도 없다. 카운터 증거는 dev 빌드 StrictMode 이중 마운트가 만드는 여분 세션과 구분되지 않아 주장보다 약하다.

읽기 전용 범위 선택 불가를 `expect(...).toBe(false)`로 고정한 판단 자체는 옳다 — 측정된 제3자 제약을 조용히 방치하지 않는다. 다만 그 단정이 지금 측정하는 것은 제약이 아니라 클릭 좌표이고, 양성 대조가 없어 제약이 풀려도 알람이 울리지 않는다.

### `pagehide` 회수가 도달하지 못하는 경로

`pagehide`를 고른 이유(`unload` 폐기·bfcache 진입 차단·모바일 미발화)는 `unload`와의 비교에서는 정확하다. 그런데 비교 대상이 하나 빠졌다. Page Lifecycle에서 **마지막으로 발화가 보장되는 콜백은 `visibilitychange` → `hidden`**이고 `pagehide`는 그보다 뒤다. 탭이 hidden으로 간 뒤 브라우저·OS가 메모리 압력으로 그 탭을 discard하거나, 사용자가 앱 스위처에서 스와이프로 죽이거나, 렌더러가 크래시하면 `pagehide`는 발화하지 않는다. 사용자가 물은 "모바일 백그라운드 종료·탭 강제 종료"가 정확히 이 구간이다.

```
정상 이탈:   visibilitychange(hidden) → pagehide → [unload]     회수 ✅
bfcache:     visibilitychange(hidden) → pagehide(persisted)     회수 ✅ / 재무장 ❌
discard:     visibilitychange(hidden) → (탭 폐기)                회수 ❌
강제 종료:   visibilitychange(hidden) → (프로세스 kill)          회수 ❌
크래시:      (아무것도 없음)                                     회수 ❌
```

세 번째 줄부터가 33초 폴백이다. 회수를 `visibilitychange:hidden`으로 옮기면 discard·강제 종료 중 상당 부분을 회수 성공으로 끌어올 수 있다 — 대신 탭 전환처럼 흔한 동작에서도 회수가 일어나므로 재무장(다음 절)이 **선택이 아니라 전제**가 된다. 지금 배선은 재무장이 없으므로 `visibilitychange`로 옮기는 것이 오히려 위험하다. 두 변경은 짝으로만 성립한다.

전송 계층에도 보장이 없다:

```js
// y-websocket/src/y-websocket.js:232
const broadcastMessage = (provider, buf) => {
  const ws = provider.ws
  if (provider.wsconnected && ws && ws.readyState === ws.OPEN) { ws.send(buf) }
  if (provider.bcconnected) { bc.publish(provider.bcChannel, buf, provider) }
}
```

큐도 재시도도 없다. "소켓이 이미 닫힌 상태에서 `setLocalState(null)`은 무엇을 하는가"의 답이 이것이다 — 로컬 상태 변경과 `update` 이벤트는 정상적으로 일어나고 전송만 무음으로 사라진다. 그리고 두 번째 `if`가 남아 있다: **BroadcastChannel로는 나간다.** 같은 브라우저의 다른 탭은 회수를 받는다. README가 권하는 "editor/viewer를 두 탭에 나눠 여는 데모"가 정확히 그 형태이므로, 데모에서는 소켓이 닫혀 회수가 실패해도 상대 탭에서 커서가 사라져 성공처럼 보인다. 하네스가 컨텍스트를 분리해 이 우회를 배제한 그 우회가 제품 데모에는 그대로 남아 있다.

정상 이탈에서도 `ws.send()`는 프레임을 소켓 버퍼에 넣고 반환할 뿐이고, 그 버퍼가 페이지 폐기 전에 플러시되는지는 스펙이 보장하지 않는다. `sendBeacon`·`fetch(keepalive)`에 있는 이탈 시 전송 보장이 WebSocket에는 없다. 측정된 2ms는 Chromium 로컬 환경의 결과다.

서버가 대신 못 한다는 것도 같은 그림의 일부다. `DocWebSocketHandler.afterConnectionClosed`는 `finishCleanup(detach(...))`만 하고 awareness 제거 프레임을 합성하지 않는다 — 페이로드를 해석하지 않는다는 §1.2 불변식 때문에 떠난 clientID를 알 수 없어서 **못 한다**. 유령 제거는 설계상 떠나는 클라이언트의 협조에만 의존한다. 그 선택 자체는 수용 가능하지만 코드와 테스트는 회수를 보장처럼 다루고, 3초 예산이 그 표현이다. 예산을 짧게 잡아 폴백 경로를 강제한 판단은 옳고, 그 예산이 **소켓이 열린 정상 reload** 하나만 덮는다는 사실이 어디에도 적혀 있지 않다.

### 회수가 하트비트를 끈다 — 재무장 부재의 2차 효과

`setLocalState(null)` 이후 `getLocalState()`는 영구히 `null`이고, presence를 다시 발행하는 모든 경로가 그 null 뒤에 잠긴다(v1이 세 지점을 확인했다: `setLocalStateField`의 `state !== null` 가드, 하트비트의 같은 가드, `websocket.onopen`의 재발행 가드). 이번 패스에서 새로 보이는 것은 그 가드가 presence만 끄지 않는다는 점이다.

```js
// y-protocols/awareness.js:61 — 15초 자가 갱신
if (this.getLocalState() !== null && (outdatedTimeout / 2 <= now - meta.lastUpdated)) {
  this.setLocalState(this.getLocalState())   // 유일한 자체 트래픽
}
```

첫째, y-websocket의 무응답 감지가 발동한다. `_checkInterval`은 `wsconnected && messageReconnectTimeout(30s) < now - wsLastMessageReceived`이면 스스로 연결을 닫는다. 그 타이머를 리셋해 주는 것은 자기 하트비트와 peer들의 하트비트다. 룸에 혼자 남은 세션이 `pagehide` 후 살아 돌아오면 양쪽이 다 없으므로 **30초마다 스스로 끊고 재접속하는 flap**이 된다(재접속 시 SyncStep1 응답이 타이머를 한 번 리셋하고 다시 30초를 센다). 증상은 "가만히 두면 주기적으로 재연결 로그가 찍힌다"이고, presence가 안 보이는 것과 원인이 같다는 연결을 짓기 어렵다.

둘째, 그 하트비트가 Phase 3 §3.4의 복구 메커니즘이다. 계획서는 fail-open의 근거를 이렇게 세운다 — "Redis가 돌아오면 다음 커서 이동이 곧 복구다. 그 사이 크로스 게이트웨이 커서는 **최대 ~15초 뒤 상대의 자가 갱신**으로 저절로 다시 보인다." 그 15초가 위 코드다. 회수한 클라이언트는 자가 갱신을 하지 않으므로, Redis 장애가 끝나도 그 클라이언트의 presence는 **다음 커서 이동이 있을 때까지** 돌아오지 않는다. 그리고 viewer는 커서를 옮기는 빈도가 편집자보다 훨씬 낮다 — 읽는 동안 아무 입력이 없는 것이 정상이다. §3.4의 자동 복구가 가장 필요한 참가자에게 가장 약하게 작동한다.

재무장(`pageshow` 또는 `resume`에서 `setLocalState({ user: awarenessUser })`)이 이 두 증상과 presence 소실을 함께 닫는다. `pagehide`에서 `event.persisted`로 분기해 bfcache 진입에서는 회수하지 않는 선택도 있지만, 그러면 복귀하지 않고 폐기되는 경우에 유령이 남는다 — 회수하고 재무장하는 쪽이 두 경우를 모두 덮는다.

### 유령의 수명은 33초가 아니다 — join 사슬로 이어진다

코드 주석과 계획서가 반복해 인용하는 "`outdatedTimeout` 30초 + 체크 주기 3초 = 약 33초"는 **한 세션 안에서의 상한**이다.

```js
// y-protocols/awareness.js:256~272 — applyAwarenessUpdate
const currClock = clientMeta === undefined ? 0 : clientMeta.clock
if (currClock < clock || (currClock === clock && state === null && ...)) {
  awareness.states.set(clientID, state)
  awareness.meta.set(clientID, { clock, lastUpdated: timestamp })   // ← 수신 시각
}
```

이미 그 clock을 아는 peer는 조건이 거짓이라 `lastUpdated`가 갱신되지 않는다 — 기존 peer의 33초 창은 연장되지 않는다. 그런데 **처음 보는 clientID는 `currClock`이 0이므로 무조건 적용되고 `lastUpdated`가 수신 시각으로 찍힌다.** 그리고 y-websocket의 queryAwareness 핸들러는 자기가 아는 상태 **전부**로 응답한다:

```js
// y-websocket/src/y-websocket.js:53~67
messageHandlers[messageQueryAwareness] = (encoder, ...) => {
  encoding.writeVarUint8Array(encoder,
    awarenessProtocol.encodeAwarenessUpdate(provider.awareness,
      Array.from(provider.awareness.getStates().keys())))   // ← 유령 포함
}
```

두 조각을 합치면 사슬이 나온다. 유령이 t=0에 떠나고 회수가 실패했다고 하자. peer P는 t=33까지 그를 쥔다. t=32에 세션 J가 join하면 게이트웨이 §1.3이 P에게 되묻고, P의 응답에 유령이 실려 J에 도착해 **J 기준 t=65까지** 살아 있다. t=64에 join한 세션은 J로부터 같은 유령을 물려받는다. join이 이어지는 동안 사슬은 끊기지 않으며, 각 홉마다 새 참가자 화면에 이미 떠난 사람의 커서가 뜬다.

사슬을 좁히는 요소가 둘 있다. 게이트웨이가 join 시 최대 3명(`MAX_QUERIED_PEERS_ON_JOIN`)에게만 질의하므로 유령을 쥔 peer가 표본에서 빠질 수 있고, 홈랩 규모에서는 join이 그렇게 촘촘하지 않다. 둘 다 확률을 낮출 뿐 상한을 만들지 않는다. Phase 3 §3.2에서 재질의가 인스턴스 경계를 넘고 응답이 룸 전원에게 가면(계획서가 N² 버스트로 이미 경고한 성질) 표본에 유령 보유자가 들어갈 확률과 사슬이 도달하는 화면 수가 함께 올라간다.

이것은 `pagehide` 회수의 가치를 깎는 관측이 아니라 반대다 — 회수 성공은 33초짜리 불편을 없애는 게 아니라 **사슬의 시작점을 없애는** 일이다. 다만 회수가 실패하는 경로의 비용을 "최대 33초"로 적어 둔 코드 주석과 계획서는 실제보다 낙관적이다.

### Phase 3에서 이 수정이 주는 안전감

회수 프레임 자체는 Phase 3를 잘 통과한다. 게이트웨이 관점에서 그것은 다른 awareness 프레임과 구분되지 않는 불투명 바이트이므로 `awareness:{docId}` fan-out을 그대로 타고 인스턴스 경계를 넘는다. §3.1이 저장 키를 0개로 유지한 결정이 여기서 배당을 준다 — 반영할 서버 상태가 없으니 회수도 릴레이만으로 끝난다.

잘못된 안전감이 생기는 지점은 셋이다.

ⓐ 앞 절의 사슬이 인스턴스 경계를 넘으면서 되살림 반경이 넓어진다. 회수가 성공한 경로는 무해하고, 실패한 경로에서 33초 창이 더 잘 뚫린다.

ⓑ §3.4의 fail-open 복구 논거가 회수에는 성립하지 않는다. "다음 커서 이동이 곧 복구"는 **가산 상태 전용**이고, 회수는 떠난 클라이언트의 마지막 프레임이라 다음 이동이 없다. Redis 장애 중 유실된 크로스 인스턴스 회수는 영구 유실이며 타임아웃 폴백만 남는다. 여기에 앞 절의 하트비트 침묵이 겹치면 **살아 있는** 클라이언트의 presence 복구까지 함께 막힌다.

ⓒ §3.1이 보류한 `presence:{docId}` Hash를 나중에 도입하면 게이트웨이는 페이로드를 해석하지 않으므로 회수 프레임을 **릴레이는 하지만 Hash에는 반영하지 못한다.** 서버 상태에 유령이 영구 잔존하고, join 시 그것을 재생하면 클라이언트의 33초 타임아웃 청소도 무력화된다 — 재생마다 새 세션의 `lastUpdated`가 갱신되므로 앞 절의 사슬이 서버 측에서 무한이 된다.

이 수정은 "어떤 서버 컴포넌트도 presence 상태를 갖지 않는다"는 불변식에 암묵적으로 의존한다. 그 의존을 `Editor.tsx` 주석에 한 줄 남기는 값이 크다 — Hash를 도입하는 사람이 프론트엔드 회수 경로를 함께 봐야 한다는 신호가 된다.

### widget decoration은 문서 모델에 닿지 않는다 — 누출은 다른 쪽에 있다

`Decoration.widget`은 `props.decorations`에서만 생성되고 문서 노드를 만들지 않으므로 Y.Doc에 아무것도 들어가지 않는다. 복사도 ProseMirror 클립보드가 라이브 DOM이 아니라 `selection.content()` 슬라이스를 직렬화하므로 위젯이 나타나지 않는다. 그리고 이 경우엔 더 강한 논거가 있다 — `LocalCaret`이 활성인 화면은 **범위 선택이 불가능한 viewer 화면**이므로 복사 경로 자체가 비어 있다(같은 PR이 `toBe(false)`로 고정한 그 제약이다). 로컬 caret이 만들 수 있는 누출 표면은 구조적으로 없다.

안정 동일성 키를 준 판단은 `WidgetType.eq`의 참조 동일성 폴백을 정확히 짚었다. 키가 없으면 원격 타이핑이 만드는 매 트랜잭션마다 caret `<span>`이 재생성돼 깜빡임 애니메이션이 0프레임에서 다시 시작한다 — 증상이 "불규칙한 점멸"이라 원인을 애니메이션 CSS에서 찾게 되는 종류의 버그다.

누출은 같은 PR의 원격 caret 렌더러에 남아 있다. `renderRemoteCaret`(`Editor.tsx:31~43`)은 라벨에 `aria-hidden`을 붙이지 않으므로, 하네스 주석이 기록한 실측 현상(`"three" + "Diag Viewer"`가 블록 `textContent`에 합쳐진다)이 테스트만의 문제가 아니라 접근성 트리와 브라우저 페이지 검색에 같은 형태로 나타난다 — 스크린리더는 peer가 커서를 옮길 때마다 그 이름을 문서 본문 중간에서 읽는다. `.collaboration-carets__label`의 `user-select: none`은 네이티브 선택만 줄이고 접근성 트리·`textContent`에는 영향이 없다. 로컬 caret에 적용한 한 줄이 원격 caret에는 빠진 비대칭이다.

그리고 하네스가 그 누출을 가린다. `documentText`는 `.collaboration-carets__caret, .collaboration-carets__selection, .local-caret`을 제거한 클론에서 텍스트를 읽는다. 문서 내용 단정을 오염에서 지키려는 의도는 맞고 필요하다 — 문제는 그 제거가 **유일한 텍스트 관측 지점**이라는 것이다. 제거 없이 읽은 텍스트가 깨끗함을 단정하는 케이스가 없으므로 라벨 누출은 하네스에 원리적으로 보이지 않는다. 제거 목록은 데코레이션 클래스가 늘어날 때마다 함께 자라고, 그때마다 눈가리개가 한 칸 커진다. 로컬 caret이 나중에 텍스트를 갖게 되면(예: 자기 이름 표시) 그 회귀도 같은 방식으로 숨는다. 제거 전 텍스트가 문서 내용과 같은지 단정하는 케이스를 하나 두면 오염 방어와 누출 감지가 분리된다.

### 하네스가 고정한 것과 놓친 것

가장 큰 간극은 **되살림 경로에 테스트가 없다**는 점이다. 이 수정의 동기는 두 단계다 — 유령이 33초 남는다는 것, 그리고 그 창 안에 재접속하면 join queryAwareness가 유령을 되살려 자기 과거 커서를 자기 화면에 띄운다는 것. 케이스 6은 첫 단계만 덮는다. `viewer().reload()` 후 `#auth-email`을 기다리고 editor 화면에서 라벨이 사라지는 것을 확인한 뒤 끝난다 — 재로그인하지 않으므로 두 번째 단계는 실행되지 않는다. 코드 주석과 계획서가 "즉시성 기능이 유령을 증폭시키는 경로"라고 길게 설명한 그 현상이 어느 계층에도 고정돼 있지 않다. 재로그인 후 자기 이름 라벨이 없음을 단정하는 케이스 하나면 닫힌다.

`blur`도 비어 있다. 플러그인이 포커스를 상태로 들고 있는 이유는 "포커스가 없는데 caret을 그리면 거짓 신호가 된다"이고 그 근거는 정확하다. 그런데 단위 테스트는 합성 `focus`만 던지고(`focusEditorSurface`), 브라우저 케이스도 caret이 생기는 것만 본다. blur에서 사라지는지는 어디에도 없다. 이 절반만 있는 검증에서 `blur` 핸들러가 사라지는 회귀는 무증상으로 통과한다.

카운터 증거는 판단은 옳고 델타의 귀속이 약하다. 하네스는 `npm run dev`(dev 빌드)를 대상으로 돌고 `src/main.tsx`가 `StrictMode`를 켜 두었으므로, **페이지 하나를 열면 effect가 두 번 실행돼 WS 세션이 두 개 만들어진다**(첫 provider는 즉시 destroy된다). 계획서에 기록된 `ws.awareness.query_sent` 델타 2가 viewer 한 명 join에 대한 값인데 실제 peer는 editor 하나뿐이므로 기대값은 1이다 — 2는 StrictMode 이중 마운트로 정확히 설명된다. 즉 `> 0` 단정은 "이 viewer 세션이 서버를 통과했다"가 아니라 "이 실행 중에 어떤 join이든 일어났다"까지만 말한다. 여기에 카운터가 룸 태그 없는 전역 카운터라는 점(`SessionMetrics:71,83`)이 겹친다. 부수적으로, 검증이 dev 빌드에서만 이루어졌으므로 프로덕션 빌드의 마운트 패턴은 이 하네스가 본 적 없다.

케이스 6에만 서버측 증거가 없는 것도 짚을 만하다. 케이스 1은 `query_sent`, 케이스 2는 `relayed` 델타를 붙였는데, 정작 이 PR이 고친 회수 경로에는 UI 부재 단정 하나뿐이다. 회수 프레임은 `relayAwareness`를 지나므로 `relayed` 델타를 함께 남길 수 있고, 그러면 "3초 안에 사라졌다"가 "명시 회수 프레임이 서버를 통과했다"로 강해진다.

CI에 갇힌 불변식은 다음이다 — 늦은 join의 3초 예산, 크로스 컨텍스트(= 게이트웨이 통과) 경로, 유령 회수의 실측 지연, 원격 selection 렌더링, viewer 자기 caret이 **실제로 그려지는지**. 이것들이 조용히 깨질 때 알려주는 것은 아무것도 없다. 단위 테스트를 배선의 존재/부재에 좁혀 함께 둔 판단은 옳고 실제로 잘 좁혀져 있다(`pagehide` 발화, 리스너 등록/해제의 핸들러 참조 동일성, `.local-caret`의 존재·부재). `focusEditorSurface`가 합성 `FocusEvent`를 던지므로 `document.activeElement`는 바뀌지 않는다 — 플러그인 상태 기계는 검증되지만 실제 포커스가 caret을 만든다는 것은 브라우저 계층에만 있다(y-tiptap의 커서 발행은 `view.hasFocus()`를 보므로 두 조건은 다르다).

### `toBe(false)`로 제약을 고정한 판단

읽기 전용에서 범위 선택이 불가능하다는 측정 결과를 단정으로 고정한 판단 자체는 옳다. 제3자 동작에 의존하는 제약을 주석으로만 적어 두면 "언젠가 되던데?" 상태로 방치되고, 실패로 알려주게 만드는 것이 그 방치를 막는 유일한 방법이다. 오해를 만드는 방식은 두 가지다.

첫째, 지금 그 단정은 제약이 아니라 클릭 좌표를 측정한다. `tryRangeSelect`는 `page.click('.editor .tiptap', { clickCount: 3 })`으로 요소 **박스 중심**을 클릭한다. `.editor .tiptap`은 `min-height: 240px`이고(`src/index.css:173~180`) 이 시나리오의 문서는 1280px 폭에서 한 줄이므로 중심 좌표는 텍스트가 없는 빈 공간이다. 제약이 나중에 풀려도 제스처가 텍스트에 닿지 않는 한 계속 `false`가 나오므로 알람이 울리지 않는다. 같은 파일의 케이스 3·4는 `box.y + 28`로 첫 줄을 정확히 찍는 기법을 이미 쓰고 있어 고치는 비용도 낮다.

둘째, 양성 대조가 없다. `selectParagraph`는 별개 함수이고 실패 시 예외를 던지므로, **같은 헬퍼가 editable 화면에서 `true`를 낸다**는 확인이 어디에도 없다. 대조가 없으면 `false`가 "제약이 있다"인지 "헬퍼가 원래 아무것도 못 한다"인지 구분되지 않는다. 대조를 붙이는 순간 이 단정은 제약을 측정하는 계기가 되고, 그때 비로소 "풀리면 실패해서 알려준다"가 성립한다.

이어지는 `expect(await remoteSelectionCount(editorPage)).toBe(0)`은 대기 없는 부재 단정이다. 릴레이가 느리면 항상 통과하므로 "selection이 발행되지 않았다"와 "아직 도착하지 않았다"를 가르지 못한다. 같은 스위트가 존재 단정에는 `waitUntil`로 시간 근거를 붙이는데 부재 단정에는 아무것도 없다.
